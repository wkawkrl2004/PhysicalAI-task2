# 파이프라인 검증: 오류와 제한 사항

`docs/PIPELINE.md`를 단계별로 검토한 결과입니다. 심각도: 🔴 계획 자체가 틀렸거나 막힐 수 있음 / 🟠 성능·일정에 큰 영향 / 🟡 구현 시 주의.
"확인 필요"는 실제 장비에서 측정해야 결론이 나는 항목입니다.

## 1. 🔴 작업 영역 중심을 잘못 잡았음
- **문제**: 과제 문서의 기준은 "**DofBot 앞 가운데 위치**를 중심으로 반지름 23cm 호"입니다. 파이프라인은 J1 회전축을 중심으로 r ≤ 23cm라고 가정했습니다.
- **영향**: J1 축에서 가장 먼 물체까지의 거리는 `23 + d0`입니다(d0 = J1 축에서 베이스 앞면 가운데까지 거리, 대략 5~8cm 예상). 즉 **최대 약 28~31cm**까지 팔을 뻗어야 할 수 있습니다. 보간·IK 범위, 검출 필터 모두 이 기준으로 바꿔야 합니다.
- **수정**:
  - 좌표 원점은 그대로 J1 축 아래에 두고, 작업 영역을 `중심 (d0, 0), 반지름 23cm` 원(앞쪽 반원)으로 정의합니다.
  - d0를 Phase C에서 측정합니다.

## 2. 🔴 수직(위에서 아래로) 집기가 가능한 범위가 매우 좁을 수 있음 — 확인 필요
- Dofbot 상완·하완(a2, a3)은 각각 8cm 안팎으로 짧고, 손목→집는 지점(a4)은 그리퍼 길이 때문에 깁니다.
- 수직 집기 조건: 손목 점이 `(r, z_grasp + a4)`에 있어야 하므로
  `√(r² + (z_grasp + a4 − h)²) ≤ a2 + a3`
- 예시 (a2 = a3 = 8.3, a4 = 17, h = 10.5, z_grasp = 2cm): r ≤ 약 14cm에서만 수직 집기가 가능합니다. 1번 항목까지 반영하면 **작업 영역의 절반 이상에서 기울여서 집어야 합니다.**
- **영향**:
  - `ik_auto_pitch`의 탐색 범위(180°→120°)로는 부족할 수 있습니다.
  - 그리퍼를 많이 기울이면 물체를 옆에서 밀어 쓰러뜨리기 쉽습니다(특히 야쿠르트 병).
- **수정**:
  - Phase C에서 링크 길이를 재자마자 위 식으로 "수직 가능 / 기울여야 함 / 불가" 영역 지도를 그립니다(1주차 최우선).
  - 피치 탐색 범위를 90°까지 넓힙니다.
  - 먼 영역은 기울여 집는 전용 접근(낮게 접근 후 수평 이동 최소화)과 시연 데이터를 따로 준비합니다.
  - 베이스에 너무 가까운 물체(r이 작음)도 팔이 접혀서 어려울 수 있으니 함께 확인합니다.

## 3. 🟠 IK 코드의 가정
| 가정 | 문제 | 수정 |
|---|---|---|
| J1 = 90 + θ | J1 회전 방향(부호)과 영점이 확인되지 않음 | J1에도 SIGN·OFFSET 적용, 보정 대상에 포함 |
| 어깨 축이 J1 축 위에 있음 | 어깨 관절이 J1 축에서 수평으로 떨어져 있으면 r이 어긋남 | 수평 오프셋 파라미터 추가 후 보정 |
| 그리퍼 끝 = 집는 지점 | 실제로 잡히는 지점은 손가락 중간 | a4를 "손가락 중간"까지로 측정 |
| 서보 2·3·4 = 90° → 팔이 수직 | Yahboom 기본값이지만 개체마다 다를 수 있음 | Phase C2에서 확인 |
| 서보 반복 정밀도 | 저가 버스 서보는 데드밴드·유격이 ±1~2°. 25cm 거리에서 어깨 1° ≈ 0.4cm, 세 관절 합치면 1cm 안팎 | 목표 오차 1cm는 빠듯함. 항상 같은 방향(위에서)으로 접근해 유격을 일정하게 유지, 손목 카메라로 최종 보정 |
| 무게에 의한 처짐 | 팔을 뻗으면 J2가 처짐 | 보정 점을 실제 집는 자세에서 기록 |

## 4. 🟠 메타 뷰 위치 추정 오차 (원근)
- 호모그래피는 **책상 평면**에 대해서만 정확합니다. YOLO bbox 중심은 물체 윗면·옆면을 포함하므로, 카메라 중심에서 먼 물체일수록 바깥쪽으로 밀려 보입니다.
- 대략 오차 ≈ 물체 높이의 절반 × (카메라 중심에서의 거리 / 카메라 높이) ≈ 2cm × 25/60 ≈ **0.8cm**.
- **수정**: 카메라를 작업 영역 중심 바로 위에 설치합니다. bbox 중심 대신 아랫부분 쪽 점을 쓰거나 높이 보정을 적용합니다. 최종 정렬은 손목 카메라 비주얼 서보잉으로 합니다.

## 5. 🟠 메타 뷰 카메라와 팔의 간섭
- 팔을 위로 세우면 높이가 40cm 이상일 수 있어, 50~60cm 높이 카메라 지지대와 부딪히거나 이동 중 화면을 가립니다.
- HOME 자세에서 팔이 베이스 근처 물체를 가릴 수 있습니다.
- **수정**: 팔을 최대로 세운 높이를 측정해 카메라 높이를 정합니다. HOME은 팔을 옆이나 뒤로 접은 자세로 하고, 검출은 반드시 HOME에서만 합니다.

## 6. 🟠 인식: 클래스 설계
- 같은 클래스 안에서도 모양 차이가 큽니다(A4 뭉치 vs 종이팩, 야쿠르트 병 vs 요플레 용기). 반대로 다른 클래스끼리는 비슷할 수 있습니다(흰 종이팩 vs 흰 요플레 용기).
- **수정**: YOLO는 **물체 종류별 세부 클래스**(a4, carton, vinyl, yakult, yogurt)로 학습하고, 결과를 3개 분리수거 클래스로 매핑합니다. 일반적으로 정확도가 더 높습니다.
- 과제에 물체 종류와 크기가 지정되어 있어서 Test 2의 차이는 주로 브랜드·색·접은 모양입니다. 생각보다 일반화 부담은 작지만, 다른 조 물체로 촬영하는 계획은 유지합니다.
- **확인 필요**: 한 세트 6개의 정확한 구성(클래스별 2개인지)을 과제 담당자에게 확인합니다.

## 7. 🟠 데이터 수집(모방학습) 방식
| 문제 | 영향 | 수정 |
|---|---|---|
| 조이스틱이 **관절을 하나씩** 움직임 | 시연이 매번 달라지고 품질이 낮음 → BC 성능 저하 | 조이스틱 입력을 IK로 연결해 **x/y/z 직교 좌표로 조작**하도록 변경 |
| 기존 코드의 이동 속도: 1°/(0.05+0.1초) ≈ 6.7°/초 | 시연이 매우 느림. 정책도 느리게 학습됨 | 스텝 크기·주기 조정 (안전 범위 내에서) |
| 두 스레드가 같은 서보 버스(I2C)에 동시에 접근 | 읽기 실패(None), 쓰기 누락 | `threading.Lock`으로 버스 접근 보호, 데이터 기록은 공유 변수(목표 각도) 사용 |
| 5~10 FPS 목표 | 카메라 2대 + JPEG 저장 + 서보 읽기를 라즈베리파이에서 처리 가능한지 미확인 | 01_camera_check에서 실제 FPS 측정 |
| 기존 코드 clamp 0~180° | J5(0~270°)에 맞지 않을 수 있음 | 관절별 범위로 clamp |
| 슬라이드의 이미지 크기 244×244 | 224×224 오타로 보임 | 224×224로 통일 |

- **현실적인 위험**: 스크립트 집기 + 비주얼 서보잉이 BC보다 성공률이 높을 수 있습니다. 두 방식을 같은 조건에서 비교하고, 시험에서는 더 나은 쪽을 씁니다(스크립트 버전을 대체가 아닌 **대안**으로 유지).

## 10. 🟡 컴퓨팅·전원·네트워크 — 확인 필요
| 항목 | 확인 내용 |
|---|---|
| Docker 컨테이너 안 PyTorch | `python3 -c "import torch, cv2"`가 되는지, Python 버전이 ultralytics 요구사항을 만족하는지. 안 되면 ONNX Runtime/NCNN으로 추론 |
| 라즈베리파이 5 CPU 추론 속도 | YOLO(NCNN/ONNX 권장) + ResNet18 두 개를 동시에 돌렸을 때 속도 측정 |
| 발열 | 연속 추론 시 쓰로틀링. 쿨러 확인 |
| 전원 | 서보 여러 개가 동시에 움직이고 CPU 부하가 높을 때 전압 저하·재부팅이 없는지 |
| 핫스팟 지연 | 노트북 추론을 쓸 경우 왕복 지연과 끊김 측정 |
| `cv2.imshow` | Jupyter(웹)에서는 창이 안 뜸. VNC 데스크톱에서 실행하거나 이미지 저장 방식 사용 |
